Streaming Shuffle for Apache Spark

Opt-in pipelined map-to-reduce data transfer
30–50% latency reduction · Zero data loss · SortShuffleManager coexistence

The Problem

  • Existing SortShuffleManager materializes full output to disk before reduce reads can start.
  • Barrier latency dominates shuffle-heavy workloads with at least 100 MB and 10 partitions.
  • CPU-bound jobs pay scheduler overhead for every shuffle.
sequenceDiagram
    participant M as Map Task
    participant D as Local Disk
    participant R as Reduce Task
    M->>D: write partition 0
    M->>D: write partition 1
    M->>D: write partition N
    Note over M,D: All partitions materialized
    R->>D: fetch partition 0
    R->>D: fetch partition 1
    R->>D: fetch partition N
    Note over R: Reads start AFTER writes complete

The Solution

    subgraph After[After Streaming Shuffle, opt in]
        M2[Map Task] -->|stream block 2MB| R2[Reduce Task]

    end
Coexists with SortShuffleManager for gradual adoption — default behavior unchanged.

Section 3: Failure Handling and Observability

Zero data loss, full visibility

Failure Handling

sequenceDiagram
    participant R as Reader
    participant P as Producer
    participant DAG as DAGScheduler
    R->>P: poll for in-progress blocks
    Note over P: Producer fails
    R->>R: detect 5s connection timeout
    R->>R: invalidate partial reads
    R->>DAG: throw FetchFailedException
    DAG->>DAG: unregisterMapOutput plus epoch bump
    DAG->>DAG: resubmit upstream stage
    Note over DAG: Recomputed producer streams to retried reader
Producer failure: 5-second connection timeout → FetchFailedException → DAG-scheduler upstream recomputation.
Consumer failure: 10-second missing acknowledgment → buffer retention → optional disk spill at 80% threshold.

Risks and Mitigations

Risk Likelihood Mitigation
Memory pressure under many concurrent shuffles Medium 80% spill threshold + LRU eviction via Guava CacheBuilder
Producer/consumer version mismatch Low StreamingShuffleFallbackPolicy detects and routes to SortShuffleManager
Network saturation Medium Token-bucket rate limit + priority arbitration in BackpressureProtocol
Telemetry overhead Low Lock-free or amortized lock acquisition; <1% CPU budget
Operator confusion (default change perception) Low Default spark.shuffle.manager=sort unchanged; opt-in via documented flag
Configuration changes require executor restart. No dynamic reconfiguration in v1.

Key Takeaway

Opt-in streaming shuffle delivers 30–50% latency reduction for shuffle-heavy workloads while preserving SortShuffleManager as the production-stable default. Zero data loss across 10 failure scenarios. Configurable, observable, and ready for gradual adoption.
