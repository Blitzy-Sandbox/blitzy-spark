Streaming Shuffle for Apache Spark

Opt-in, low-latency shuffle with automatic fallback

spark-core 2.13 4.2.0-SNAPSHOT Zero-regression by design
The problem

Sort-based shuffle adds latency

  • Map output is fully materialized to local disk before any reduce-side fetch begins.
  • Reducers wait for producers to finish writing — latency compounds at scale.
  • Shuffle-heavy pipelines pay this cost at every stage boundary.
For large jobs (≥ 100 MB, ≥ 10 partitions), the write-then-fetch barrier dominates end-to-end time.
The solution

Stream the data instead of staging it

Stream intermediate data producer → consumer through bounded in-memory buffers over the existing network transport, governed by backpressure.

Capabilities

Five core capabilities

  • Producer → consumer streaming over the existing transport.
  • Bounded in-memory buffering — default 20% of executor memory (range 1–50%).
  • Backpressure — heartbeat + token-bucket rate limiting.
  • Graceful disk spill at the 80% utilization threshold.
  • Partial-read invalidation → FetchFailedException → recompute.
Opt-in by design

Zero change to default behavior

spark.shuffle.manager=streaming
AND
spark.shuffle.streaming.enabled=true
Both flags default OFF. Until both are set, behavior is byte-for-byte unchanged — existing clusters are entirely unaffected.

Coexistence

Sort-based shuffle is the safety net

  • StreamingShuffleManager holds a lazy inner SortShuffleManager.
  • It delegates when streaming is disabled or any fallback condition trips.
  • The sort path is never modified — it is composed unchanged.
Fallback is the zero-regression guarantee: unsuitable workloads revert to sort-based shuffle automatically.
Automatic fallback

Four revert conditions

Slow consumer
Consumer sustained 2× slower than producer for > 60 s.
Memory pressure
Buffer allocation at OOM risk (> 95%).
Network saturation
> 90% of link capacity.
Version mismatch
Producer / consumer version mismatch.
Safety & correctness

Zero data loss by construction

  • CRC32C block checksums validate every 2 MB block on the wire.
  • Partial-read invalidation on a 5 s connection timeout raises FetchFailedException.
  • Spark's existing lineage recomputes the lost output — no new recovery model.
Zero data loss under all failure scenarios.

Risks & mitigations

Every risk has a built-in mitigation

Risk Mitigation
Misconfiguration (only one flag set)Dual-flag opt-in + documented activation; one flag alone stays on sort-based shuffle.
Memory pressure / OOM riskSpill at the 80% threshold (< 100 ms) and automatic fallback to sort.
Consumer slower than producerBackpressure (heartbeat + token bucket); fallback if sustained 2× for > 60 s.
v1 transport is logging-onlyBy design — the real data plane is the existing BlockTransferService / fetchBlockSync (documented in the decision log).

Getting started

Enable, tune, measure

Enable both flags in spark-defaults.conf (manager + feature flag).
Tune bufferSizePercent, spillThreshold, and maxBandwidthMBps for the workload.
Config is immutable for the app lifetime — restart to change. See the Configuration & Operator guides.
spark.shuffle.manager            streaming
spark.shuffle.streaming.enabled  true
spark.shuffle.streaming.bufferSizePercent  20
spark.shuffle.streaming.spillThreshold     80
