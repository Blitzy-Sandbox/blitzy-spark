BLITZY Executive Summary
The Problem

Shuffle latency is paid up front

Sort-based shuffle materializes intermediate data to local disk before any reduce-side fetch can begin. That write-then-read round trip adds latency to every shuffle-heavy stage.

Reducers stay idle while map output is flushed and indexed — latency that scales with data volume and partition count.
Map writes outputRecords are partitioned and serialized.
Materialize to diskFull spill of data and index files before fetch.
Reduce waitsNo data moves until materialization completes.
Then fetchOnly now can reducers pull their partitions.
The Solution

Stream, don't materialize

Stream intermediate data producer to consumer through bounded in-memory buffers over the existing network transport, governed by backpressure — so reducers consume data as it is produced.

Buffer in memoryPer-partition buffers replace the full disk spill.
Pipeline over the networkReuses Spark's existing block transport — no new data plane.
Govern with backpressureHeartbeat, ack, and token-bucket rate limiting over the executor RPC endpoint keep producers in step with consumers.
Delivered as a self-contained, opt-in backend that coexists with — and falls back to — sort-based shuffle.

Capabilities

Five core capabilities

Producer to consumer streamingMap output is pipelined to reducers instead of fully materialized first.
Bounded in-memory bufferingPer-partition buffers default to 20% of executor memory (configurable 1–50%).
Backpressure flow controlConsumer heartbeat, ack, and token-bucket rate limiting throttle producers over the per-executor RPC endpoint (co-located in v1; remote auto-discovery in v2).
Graceful disk spillThe largest buffers spill at 80% utilization, reclaiming memory in under 100 ms.
Partial-read invalidationOn producer failure, partial reads are invalidated and surfaced as FetchFailedException.
Opt-in by Design

Zero change to default behavior

The streaming backend engages only when an operator enables both signals. Either flag alone keeps the cluster on sort-based shuffle.

spark.shuffle.manager=streaming default: OFF
spark.shuffle.streaming.enabled=true default: OFF
Both default OFF — the default behavior of every existing Spark deployment is byte-for-byte unchanged.

Coexistence

Automatic, safe fallback

StreamingShuffleManager holds a lazy inner SortShuffleManager and delegates to it whenever streaming is disabled or any fallback condition trips. The sort-based path is never modified.

Streaming activeEnabled and healthy: data is streamed producer to consumer.
Automatic fallbackLive signals from backpressure and spill feed the manager-owned policy; registerShuffle routes unsuitable shuffles to the inner sort manager.
Production-wired and verified: backpressure pushes throughput/network samples, the spill manager pushes memory utilization, and the decision is taken at shuffle registration — proven by StreamingShuffleManagerSuite delegating to the unchanged SortShuffleManager.
Fallback Triggers

Four conditions revert to sort

Slow consumerConsumer sustained 2x slower than producer for over 60 s.
Memory pressureBuffer allocation would risk OOM (above 95% memory).
Network saturationLink utilization above 90% capacity.
Version mismatchProducer and consumer versions differ. Trigger wired in v1; on-wire auto-detection lands in v2.
Three of the four conditions trip automatically from live executor signals today; version-mismatch auto-detection is deferred to v2 with the transport hardening (see the decision log).
Safety & Correctness

Zero data loss by construction

CRC32C block checksumsEvery 2 MB block is checksummed and verified on read.
Partial-read invalidationOn a 5 s connection timeout the reader invalidates partial reads and raises FetchFailedException.
Recompute via existing lineageSpark's unchanged fault-recovery machinery recomputes the lost upstream output.
Zero data loss under all failure scenarios — correctness is delegated to mechanisms Spark already trusts.

Getting Started

Enable in three steps

1Opt in. Set both flags in spark-defaults.conf.
2Tune. Adjust bufferSizePercent, spillThreshold, and maxBandwidthMBps.
3Learn more. Consult the Configuration and Operator guides in this section.
# spark-defaults.conf spark.shuffle.manager streaming spark.shuffle.streaming.enabled true spark.shuffle.streaming.bufferSizePercent 20 spark.shuffle.streaming.spillThreshold 80 spark.shuffle.streaming.maxBandwidthMBps -1 # default -1; <=0 = unlimited spark.shuffle.streaming.debug false
Configuration is immutable for the application lifetime — restart the executor to change it (no dynamic reconfiguration in v1).
