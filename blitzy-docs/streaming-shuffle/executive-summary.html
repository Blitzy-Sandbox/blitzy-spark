Streaming Shuffle
for Apache Spark

Opt-in, low-latency shuffle that coexists with sort as a production-stable fallback.

Apache Spark 4.2.0 Feature: Streaming Shuffle Zero-regression by design

The Problem

Sort-based shuffle materializes all map output to local disk before any reduce task can begin.

  • Full materialization adds latency to shuffle-heavy pipelines.
  • Reduce tasks stall on the slowest map write plus disk I/O.
  • Intermediate data is written, then re-read — pure overhead for pipelines that could stream.
Today: sort-based shuffle
Map→ Disk→ Reduce

Every byte lands on disk before it can be read back.

The Solution

Streaming shuffle pipelines map output directly to reducers through bounded in-memory buffers, governed by backpressure.

  • Opt-in — enabled per application; sort remains the default.
  • Coexists with sort-based shuffle as a production-stable fallback.
  • Isolated — all logic lives in a dedicated shuffle.streaming package.
Streaming shuffle
Map→ In-memory buffer→ Reduce

Data flows while it is produced — no full disk materialization on the happy path.

Key Design Decisions

Composition fallback

Hold an inner SortShuffleManager and delegate all non-streaming handles. Sort internals are never touched.

Reuse, don't rebuild

Least modification: BlockTransferService, MemoryConsumer, and MetricsSystem are reused as-is.

Dual activation gate

Defense-in-depth opt-in — two independent flags must both be set to activate streaming.

JDK 17 CRC32C

Built-in java.util.zip.CRC32C — zero third-party checksum dependency.

Guava RateLimiter & Cache

Already Spark Core dependencies — proven rate limiting and an LRU spill store.

Standard fault path

Producer timeout throws FetchFailedException; the DAG scheduler recomputes — no scheduler changes.

Dual Activation Gate

Streaming shuffle is active if and only if both conditions hold:

Backend selected

spark.shuffle.manager=streaming — resolves through the existing factory alias.

Feature enabled

spark.shuffle.streaming.enabled=true — opt-in flag (default false).

Immutable configuration

No dynamic reconfiguration in v1 — changing any key requires an executor restart.

Backend class

org.apache.spark.shuffle.streaming.StreamingShuffleManager

Automatic Fallback (zero regression)

On any of four conditions, the manager delegates to the inner sort path:

Slow consumer

Consumer sustained ≥2× slower than the producer for >60 s.

Memory pressure

Utilization near ~95% — buffer allocation would risk OOM.

Network saturation

Link utilization exceeds ~90% of capacity.

Version mismatch

Producer / consumer compatibility check fails.

80% utilization → spill · stays streaming vs ~95% pressure → fallback to sort

Failure Handling & Zero Data Loss

  • 5 s producer timeout → atomically invalidate the partial read.
  • Throw the standard FetchFailedException → DAG upstream recompute.
  • CRC32C per 2 MB block detects corruption → retransmit.
  • Retry with exponential backoff — 1 s start, max 5 attempts.
  • 10 s consumer heartbeat for liveness; decommission migration preserved.
Recovery path
Producer crash / timeout (5 s) ↓ Invalidate partial read (atomic) ↓ FetchFailedException ↓ DAG recomputes upstream
