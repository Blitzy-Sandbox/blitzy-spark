Streaming Shuffle · Executive Summary
The Problem

The materialization barrier

Sort-based shuffle writes every map output to local disk, then reduce tasks fetch it back over the network. That write-to-disk-then-fetch step is a hard materialization barrier: producers and consumers never overlap, so shuffle-heavy stages pay full disk-write + fetch latency before any reduce work can begin.

Map task produces Spill to local disk Network fetch Reduce waits
For latency-sensitive, shuffle-heavy pipelines (≥ 100 MB, ≥ 10 partitions) the disk round-trip dominates end-to-end time — precisely the gap push-based shuffle (Project Magnet) does not target.
Streaming Shuffle · Executive Summary
The Solution

Stream the data, skip the barrier

A new StreamingShuffleManager SPI implementation pipes shuffle blocks directly from producer to consumer through bounded in-memory buffers governed by a backpressure protocol — and it coexists with, never replaces, the default sort path.

Opt-in & pluggable
Selected via spark.shuffle.manager=streaming; default stays sort. Reflective factory needs no change.
Bounded buffers + backpressure
Per-partition in-memory buffers capped at a configurable % of executor memory; token-bucket flow control prevents overrun.
Graceful degradation
Holds an inner SortShuffleManager by composition and falls back automatically on any risk condition.

Activation & Configuration

The dual-flag activation contract

spark.shuffle.manager=streaming AND spark.shuffle.streaming.enabled=true

If either flag is absent, the inner SortShuffleManager handles all shuffle — behavior is identical to stock Spark. Keys are immutable for the application lifetime (no dynamic reconfiguration in v1) and range-validated fail-fast.

Flow Control

Backpressure protocol

Consumer-to-producer flow control: a token bucket (one permit = one byte) capped at 80% of link capacity, plus a 5 second heartbeat, carried over an executor-only ThreadSafeRpcEndpoint. Token accounting is lock-free (AtomicLong); acknowledgments merge monotonically so duplicates never regress the watermark.

Memory Safety

Memory & spill management

80%
Spill threshold
Sustained utilization near 80% triggers a disk spill before memory is exhausted.

The MemorySpillManager polls buffer utilization every 100 ms. At the 80% threshold it spills the largest partitions (LRU) to disk via BlockManager.putBytes(…, DISK_ONLY) — reusing the storage contract, never altering it — and reclaims buffers within 100 ms of acknowledgment.

Safety Envelope

Fallback & zero data loss

StreamingShuffleFallbackPolicy (F-111) reverts a shuffle to the inner sort path on any of four conditions; every failure path invalidates cleanly and defers to Spark's existing recomputation.

Slow consumer
Consumer sustained 2× slower than producer for > 60 s.
Memory pressure
Buffer allocation would risk OOM.
Network saturation
> 90% link capacity utilized.
Version mismatch
Producer / consumer versions differ.
Zero data loss invariant
Producer timeout, checksum mismatch, or consumer crash → invalidate partial read → FetchFailedException → DAG recompute.

Failure-injection scenarios validated for zero data loss

v1 Scope

One intentional v1 deviation

The v1 network transport StreamingShuffleTransport (F-115) ships as a logging-only stub that reuses the executor's existing BlockTransferService and introduces no new TransportContext. This is the single documented, intentional exception to the no-placeholder rule — recorded in the decision log.
Self-describing wire
StreamingBlockEnvelope (F-116): 32-byte big-endian header + ≤ 2 MiB payload + CRC32C.
Immutable config
Keys read once at construction; no dynamic reconfiguration in v1.
Explainability
Every non-trivial decision captured in decision-log.md with a traceability matrix.
