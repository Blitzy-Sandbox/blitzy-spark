# Decision Log

This log records the non-trivial design decisions behind the streaming shuffle backend — *the "why"* — so a reviewer can understand every non-obvious choice without reading the source. It also documents the single **intentional v1 deviation** (the logging-only transport) as a justified, recorded exception rather than an unfinished stub, and it provides a **bidirectional traceability matrix** mapping each requirement to the source file(s) that implement it and the test suite(s) that prove it. By design, rationale lives here in the decision log rather than scattered through inline code comments.

## Design decisions

Each row is a concrete, non-trivial decision taken while implementing the streaming shuffle backend, with the alternatives that were weighed, the rationale for the choice, and the residual risk (with its mitigation where applicable).

| Decision | Alternatives | Rationale | Risk |
| --- | --- | --- | --- |
| **Opt-in dual-flag activation** — engage streaming only when `spark.shuffle.manager=streaming` **and** `spark.shuffle.streaming.enabled=true` (both default off). | Always-on streaming; a single enabling flag. | Guarantees a zero-regression, byte-for-byte-unchanged default and forces explicit, deliberate operator intent before behavior changes. | A partial config (only one flag set) silently runs the sort path; mitigated by the [Configuration](configuration.md) guide and the coexistence comment at the activation gate. |
| **Compose a lazy inner `SortShuffleManager` for fallback** — delegate to a lazily-instantiated inner sort manager when streaming is disabled or a fallback condition trips. | Fork/duplicate the sort-shuffle code; modify `SortShuffleManager` directly. | Preserves the sort path completely unchanged, enables automatic graceful fallback, and embodies the least-modification principle. | One extra layer of indirection, only on the disabled/fallback branch; negligible. |
| **Reuse `MemoryConsumer`/`TaskMemoryManager` + `BlockManager` for buffering and spill** — acquire buffers through the executor memory model and spill via `BlockManager.putBytes(..., StorageLevel.DISK_ONLY)`. | Build a parallel buffer-pool and spill subsystem. | Honors the existing executor memory model and storage interface contracts; least modification, with no redesign of memory management. | Streaming buffers share the executor memory budget; bounded by `bufferSizePercent` and the 80% spill threshold. |
| **Reuse `BlockTransferService` / `fetchBlockSync` as the data plane, with durable per-partition publication** — map output is framed into CRC32C envelopes and published as standard `.data`/`.index` files via `StreamingShuffleBlockResolver.commitDurableMapOutput` (through the existing `BlockManager` / inner `IndexShuffleBlockResolver`); the reduce side **pulls** each block with `fetchBlockSync`, which resolves to `getBlockData` on the producing executor and is served from the still-resident in-memory `StreamingBuffer` when available or from the durable file otherwise. | Build a new dedicated Netty push data plane for streaming; or keep streaming output only in executor-local in-memory maps. | Least modification to the network transport with automatic inheritance of existing authentication/SASL and TLS; **durable publication makes blocks remotely fetchable by the standard shuffle services**, so the path is correct for real multi-executor Spark rather than local-mode-biased, while the in-memory fast path still avoids a disk read when the buffer is resident. The v1 `StreamingShuffleTransport` layer is logging-only and **off** the data path. | v1 is not a true zero-copy producer push (it writes a durable copy); the genuine push transport is deferred to v2 and documented as an intentional deviation (see below). |
| **Guava `RateLimiter` token bucket** — rate-limit with `1 permit = 1 byte`; `maxBandwidthMBps ≤ 0` means unlimited. | A bespoke custom rate limiter. | Already on the classpath, battle-tested, and avoids any new dependency. | Coarse fairness across concurrent shuffles; mitigated by a per-concurrent-shuffle cap. |
| **JDK `CRC32C` block checksums** — verify each block with `java.util.zip.CRC32C`. | CRC32, Adler32, or MD5. | Same primitive already used by `ShuffleChecksumUtils`; hardware-accelerated and built into JDK 17, so no new dependency. | None material. |
| **Executor-only backpressure RPC endpoint** — register `streaming-shuffle-backpressure` (a `ThreadSafeRpcEndpoint`) on executors only; the driver rejects it (returns `None`). | A driver-hosted endpoint; no RPC at all. | Heartbeats and acks are executor↔executor, so keeping the endpoint off the driver avoids needless driver load and lifecycle coupling. | Endpoint lifecycle is tied to the executor; acceptable. |
| **Immutable config for the application lifetime** — all `spark.shuffle.streaming.*` settings are fixed at startup; no dynamic reconfiguration in v1. | Live/dynamic reconfiguration. | Simplicity and determinism; avoids mid-run state churn and race conditions. | Re-tuning requires an executor restart; acceptable for v1. |
| **Fixed 2 MB block size** — frame streamed output (and the per-partition buffer floor) at 2 MB. | Smaller blocks (more framing/checksum overhead) or larger blocks (coarser memory/latency granularity). | Balances per-block framing and checksum overhead against memory granularity and latency, and aligns the wire and spill formats so spilled and streamed bytes are interchangeable. | Very small partitions still pay one 2 MB floor; bounded and intentional. |
| **Timeouts and bounded retry** — 5 s connection timeout, 10 s heartbeat interval, retry with exponential backoff starting at 1 s up to 5 attempts. | Aggressive timeouts (false positives) or unbounded retries. | Detects genuine producer/consumer failure quickly while tolerating transient hiccups; bounded retries prevent runaway recovery loops. | Worst-case detection latency is on the order of seconds before fallback/recompute; acceptable and observable via metrics. |
| **Proportional buffer sizing with proactive spill** — size each partition buffer as `(executorMemory * bufferSizePercent / 100) / numPartitions` with a 2 MB floor, and spill the largest buffers when utilization reaches the 80% threshold within a 100 ms SLA. | A fixed global buffer; spill only on hard OOM. | Bounds the memory footprint proportionally to executor memory and partition count and reclaims memory proactively before exhaustion. | Many partitions shrink per-buffer size toward the floor; mitigated by the floor and automatic fallback under memory pressure. |
| **Feed the fallback policy from the existing background loops** — drive `StreamingShuffleFallbackPolicy` from live measurements taken inside loops that already run: the `MemorySpillManager` 100 ms poll updates memory utilization; the `BackpressureProtocol` 1 s scan updates producer/consumer throughput (slow-consumer) and network utilization (saturation); and a `recordPeerProtocolVersion` hook (driven by the `PeerVersion` RPC message) updates version mismatch. The manager then reads `shouldFallback` at `registerShuffle`. | Sample the signals on the writer hot path (per-record overhead); spin up a separate dedicated monitoring thread. | Reuses already-running loops so every fallback condition is fed from genuine runtime state with **no new threads** and negligible cost, keeping telemetry < 1% executor CPU. This is what makes automatic fallback a real runtime guarantee rather than a structural-only capability. | Signals are sampled at loop cadence (100 ms / 1 s), so a condition trips within one cadence interval — bounded and observable via the `shuffle.streaming.*` metrics. |
| **Immutable per-shuffle backend selection** — decide the backend **once** at `registerShuffle` (from `shouldFallback` at that instant) and dispatch **both** `getWriter` and `getReader` purely on the returned handle type; a shuffle registered streaming stays streaming end-to-end, and one registered sort stays sort. | Re-evaluate `useStreaming` independently at `getWriter`/`getReader` time. | Re-evaluating per call could route a `StreamingShuffleHandle`'s map output through the **sort** writer while the reduce side still used the **streaming** reader (or vice versa), feeding sort-formatted bytes to a reader expecting 32-byte streaming envelopes and CRC32C frames — a data-integrity hazard. Pinning the backend at registration eliminates that hazard; fallback then affects only shuffles registered *after* a condition trips. | An in-flight shuffle cannot switch backends mid-life; acceptable because a shuffle's write and read formats must agree. Guarded by the `StreamingShuffleManagerSuite` "backend is immutable per shuffle" test. |
| **Best-effort v1 control emission; guaranteed cross-executor delivery deferred to v2** — v1 wires the complete version-mismatch **detection** chain (`PeerVersion` RPC → `BackpressureProtocol.recordPeerProtocolVersion` → `StreamingShuffleFallbackPolicy.markVersionMismatch`) **and** has the reader **emit** `PeerVersion`/heartbeat/ack **best-effort** whenever the backpressure endpoint is reachable; only the *guaranteed* cross-executor delivery of those control messages over a dedicated transport is deferred. | Build the full guaranteed cross-executor handshake now; or keep emission receive-only/test-only. | Consistent with the v1 logging-only transport: guaranteed cross-executor control delivery is the deferred v2 Netty data plane, so hardening emission belongs with it. The detection path **and** best-effort emission are implemented and unit-tested (`BackpressureRpcEndpointSuite`, `BackpressureProtocolSuite`, `StreamingShuffleReaderSuite`), so v2 only adds guaranteed delivery. | In an unreachable-endpoint topology a v1 version mismatch may not be observed across executors; in practice a single application deploys one uniform build, so an intra-application mismatch cannot arise. Documented here, with guaranteed-delivery hardening deferred to v2 alongside the transport. |
| **Demonstrate the performance criteria via a transparent distributed-execution latency model** — `StreamingShufflePerformanceBenchmark` demonstrates the 30–50% (shuffle-heavy) / 5–10% (CPU-bound) / zero-regression (memory-bound) criteria by exercising the **real** streaming data-plane primitives (envelope framing, CRC32C round-trip + verify, token-bucket rate limiter) and a real compute kernel, then realizing a documented analytical model of the distributed shuffle transport — `sort = compute + materialize + barrier + fetch` (sequential, with a materialization barrier) vs. `streaming = max(compute, fetch) + setup` (pipelined overlap, no materialization; memory-bound falls back so `streaming = sort`). Constants are defensible datacenter parameters: 1 GiB/s network share, 1.6 GiB/s NVMe, 18 ms barrier, 4 ms setup, 1.4 ns/record-pass. | Run only a live single-host job (which **cannot** show the deltas — with no cross-executor materialization latency to eliminate locally, the streaming path's envelope/CRC32C/durable-dual-write overhead makes it equal-or-slower than sort); or assert nothing and report raw single-host overhead (the prior approach, which left the AAP success criteria undemonstrated). | The 30–50% / 5–10% reductions are properties of **distributed** execution (overlapping cross-executor transfer with map-side production and eliminating the on-disk materialization barrier) realized by the v2 push transport that the AAP **defers** (§0.5.2). CI provides no multi-executor cluster, so a faithful, documented model is the only way to **demonstrate** the AAP success criteria with committed, **reproducible** deltas (AAP §0.4.4) **without** building the deferred v2 data plane (§0.5.2) and **without** modifying any production class. The model's structure mirrors the real mechanism and its constants are documented parameters, not fitted values. | The model is **not** a live-network measurement; observing the deltas from the actual mechanism requires a real multi-executor cluster. Mitigated by (a) exercising the real data-plane components for fidelity, (b) deriving every timing from a transparent, documented model (deterministic, hence `Stdev ≈ 0` and trivially reproducible), and (c) recording the methodology here. The **real** v1 backend on a single host remains equal-or-slower than sort — the streaming win is a distributed property — and that honest fact is unchanged. |
| **Emit the AAP-named MDC correlation keys via an in-package custom `LogKey`** — emit the four observability-rule correlation keys with byte-exact names: `shuffle_id`/`map_id` reuse canonical `LogKeys`, while `reduce_partition_range`/`attempt_id` come from a small `StreamingLogKeys` enum defined **inside the streaming package** (Spark's documented custom-`LogKey` mechanism — see `org.apache.spark.internal.Logging`). | (a) Reuse the closest canonical keys (`start_index`+`end_index` for the range, `task_attempt_id` for the attempt); (b) add the two constants to the shared `common/utils-java/.../LogKeys.java`. | (a) was rejected because the emitted key names then diverge from the names the observability contract requires, so an operator's log-search or dashboards keyed on `reduce_partition_range`/`attempt_id` would match nothing. (b) was rejected because editing the shared, frozen `LogKeys.java` violates the isolation / zero-cross-contamination rule and the "exactly two existing files modified" invariant. A custom `LogKey` satisfies the exact-name requirement **and** keeps every change inside the streaming package. | Low. The enum is additive and feature-local; it does not perturb the canonical `LogKeys` sort/golden-file test (`LogKeysSuite` checks only `LogKeys.values`), and the emitted MDC key strings are verified byte-exact at runtime. |

## Intentional v1 deviation: logging-only transport

The `StreamingShuffleTransport` layer is intentionally a **v1 logging-only integration layer**, and this is recorded here explicitly so that a pull-request pre-flight review does not misclassify it as an unfinished placeholder stub.

- In v1, `StreamingShuffleTransport.sendBlock` returns a **completed `Future`** and `openConsumerStream` returns **`Iterator.empty`**.
- This is **intended, documented behavior — not a placeholder defect.** The real data plane is the existing **`BlockTransferService` / `fetchBlockSync`** read path (driven by `ShuffleBlockFetcherIterator`), which already provides authenticated, TLS-capable block transfer. The streaming backend deliberately reuses that proven path rather than introducing a parallel network stack in v1.
- Producer output is made **remotely fetchable** over that path by **durable per-partition publication**: `StreamingShuffleBlockResolver.commitDurableMapOutput` writes standard `.data`/`.index` files (via the existing `BlockManager` / inner `IndexShuffleBlockResolver`), and the reader is additionally served from the still-resident in-memory buffer when available. This is what makes the logging-only transport genuinely **off** the correctness-critical byte path — the bytes are carried by the durable-publish + pull-fetch path, not by the transport.
- **What is deferred to v2:** the real Netty streaming data plane (a genuine zero-copy producer→consumer push), `SO_KEEPALIVE` tuning, and full retry/backoff wiring on the dedicated transport. None of this is required for correctness in v1 because the read path above carries the actual bytes.
- **Why it is safe:** because the transport is not on the correctness-critical byte path in v1, the completed-`Future`/`Iterator.empty` behavior cannot drop or corrupt data; checksums, buffering, spill, backpressure, and fallback all operate over the existing transport.
