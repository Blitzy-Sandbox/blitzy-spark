# Streaming Shuffle — Decision Log

## Purpose

This document is the **single source of truth for "why"** behind every
non-trivial design decision in the Streaming Shuffle implementation added to
Apache Spark 4.2.0-SNAPSHOT. It satisfies the Explainability Rule (AAP §0.7.7)
by documenting each decision, the alternatives that were considered and
rejected, the rationale anchored in user requirements or AAP constraints, and
the risks (with mitigations) carried by the chosen approach.

Rationale MUST NOT be embedded in code comments — this file is the
authoritative log. Source comments describe **what** the code does; this log
describes **why** that approach was chosen. Future deviations from these
decisions require a new (superseding) entry rather than edit-in-place, so the
history of reasoning is preserved.

## Methodology

Each decision recorded here satisfies four criteria:

1. It resulted in a non-obvious choice between two or more technically viable
   options.
2. Its rationale traces to at least one user requirement (AAP §0.1) or AAP
   constraint (§0.6, §0.7).
3. At least one plausible alternative was evaluated and rejected.
4. At least one risk was identified, with a mitigation where available.

## Requirement ID Taxonomy

Decisions cite requirement IDs using the taxonomy defined in
[streaming-shuffle-traceability.md](./streaming-shuffle-traceability.md) and
reused across [streaming-shuffle.md](./streaming-shuffle.md):

| Prefix | Meaning | Example |
|--------|---------|---------|
| `SC-*` | Success Criteria | `SC-1` = 30-50% latency reduction for shuffle-heavy workloads |
| `CR-*` | Component Responsibilities (M = Manager, W = Writer, R = Reader, B = Backpressure, S = Spill) | `CR-B-2` = token-bucket rate limiting at 80% link capacity |
| `IC-*` | Implementation Constraints | `IC-10` = CRC32C checksum algorithm |
| `AP-*` | Absolute Preservation invariants | `AP-5` = zero modification to `SortShuffleManager` |
| `ID-*` | Implementation Discipline directives | `ID-3` = least modification to executor memory model and network transport |
| `FH-P-*` / `FH-C-*` | Failure Handling, Producer / Consumer side | `FH-P-1` = 5-second connection timeout |
| `FB-*` | Automatic Fallback conditions | `FB-3` = >90% network saturation |

| **D1. Integrate via `ShuffleManager` SPI (Option A), not `ShuffleDataIO` plug-in (Option B).** `StreamingShuffleManager` implements the `ShuffleManager` trait directly; a new `"streaming"` short-name is registered in the `shortShuffleMgrNames` companion map. | (a) **Option B** — implement streaming as a `ShuffleDataIO` plug-in supplying custom `ShuffleExecutorComponents` and `ShuffleMapOutputWriter` while reusing `SortShuffleManager` framing. (b) **Option C** — subclass `SortShuffleManager` and override `getWriter` / `getReader` (rejected outright; violates AP-5). | Streaming shuffle needs to own the map-output byte path end-to-end. The `ShuffleDataIO` contract (`ShuffleMapOutputWriter.getPartitionWriter(reducePartitionId)`) assumes post-sort materialization with a monotonically-increasing partition-writer contract and file-index commit semantics, which contradict streaming's in-progress consumption model. Option A provides full control over `getWriter` / `getReader` without disturbing the production-stable sort path (**AP-5, ID-2, ID-4**). The existing selector map in `ShuffleManager.scala:112-114` accommodates a new short-name entry with a pure append (**ID-1**). | Duplicates some plumbing (handle class, writer lifecycle, resolver) that Option B would inherit from `SortShuffleManager`. **Mitigation**: internally delegate the spill byte path to `LocalDiskShuffleDataIO` via `ShuffleDataIOUtils.loadShuffleDataIO(conf)` so that spilled blocks remain plug-in-addressable and honor ADR-002 atomic metadata commit. |
| **D2. Token-bucket rate limiting via Guava `com.google.common.util.concurrent.RateLimiter`**, wrapped by `TokenBucketRateLimiter.scala`, with dynamic `setRate(maxBandwidthMBps * 1024 * 1024 / numConcurrentShuffles)`. | (a) **Leaky-bucket** producing smooth constant-rate output with no burst capacity. (b) **Hand-rolled** rate limiter using `AtomicLong` timestamps and `LongAdder` counters without Guava. (c) **Netty `TrafficShapingHandler`** applied at channel level. | Token-bucket allows bursts up to bucket capacity, which matches streaming shuffle's natural bursty output pattern (aggregated record batches flushed in bulk after partitioner grouping). Guava is already a transitive dependency on the core classpath (**AAP §0.3.1**) — zero new dependencies (**ID-3, §0.7.8 invariant**). `RateLimiter.setRate()` supports dynamic recalculation as `numConcurrentShuffles` changes (**CR-B-2**). Leaky-bucket's fixed output rate would under-utilize the link during low-concurrency windows. | Guava `RateLimiter` uses an internal `Stopwatch` not bound to the `TaskMetrics` clock; could drift under extreme clock skew or JVM GC pauses >1s. **Mitigation**: clock drift is negligible at millisecond rate-limit granularity, and the `JvmPauseMonitor` already alerts on long pauses. Also Guava `RateLimiter` is explicitly marked `@Beta` — **Mitigation**: the API has been stable since Guava 13 (2012) and has been consumed by Spark's existing code paths for >10 years. |
| **D3. CRC32C checksum via `java.util.zip.CRC32C` (JDK 17 built-in)** applied to every `StreamingBlockEnvelope` payload before transmission and verified on receipt. | (a) **Murmur3** via Guava `Hashing.murmur3_32_fixed()`. (b) **Adler32** via JDK `java.util.zip.Adler32`. (c) **xxHash64** via a third-party library (e.g., `net.jpountz.xxhash`). | **IC-10** explicitly specifies "CRC32C for block integrity validation". JDK 17 provides `java.util.zip.CRC32C` (introduced JDK 9) — no third-party dependency required (**ID-3**). CRC32C has hardware acceleration via SSE 4.2 (x86 `CRC32` instruction) and Armv8 CRC extensions, yielding ~1 GB/s single-core throughput, comfortably satisfying **IC-14** (<1% CPU telemetry overhead). Murmur3 and xxHash64 are non-cryptographic hashes better suited to hash tables than integrity; Adler32 has known weak bit-diffusion properties for short payloads. | CRC32C is integrity-only, not authentication; a man-in-the-middle could recompute a valid checksum over forged bytes. **Mitigation**: streaming traffic inherits the existing `TransportContext` transport envelope — `spark.authenticate` (SASL), `spark.network.crypto.enabled` (AES-GCM), and TLS protect against tampering (**AAP §0.7.5**). CRC32C's role is detection of wire corruption and memory corruption, not adversarial integrity. |
| **D4. Separate `BackpressureRpcEndpoint` on `NettyRpcEnv` for heartbeats and ACKs**, registered under endpoint name `"streaming-shuffle-backpressure"`, symmetric to `BlockManagerMasterEndpoint`. Bulk data travels via `TransportContext`; control plane travels via `NettyRpcEnv`. | (a) **Piggyback ACK metadata** on the existing `TransportContext` client messages (e.g., in `ChunkFetchRequest` response headers). (b) **Dedicated Netty `ChannelHandler`** inline in `StreamingShuffleTransport`. (c) **Driver-coordinated ACKs** routed through a new driver-side endpoint. | Reusing `NettyRpcEnv.setupEndpoint(name, endpoint)` follows an established Spark pattern (**AAP §0.4.1.2**) and introduces no new transport framing (**ID-3**). Separating bulk-data from control-plane traffic prevents head-of-line blocking on the control path when a producer's data channel is saturated. `ThreadSafeRpcEndpoint` naturally supports the 10-second periodic heartbeat invocation required by **CR-B-1** without additional scheduling machinery. | Adds a second network round-trip for ACKs vs. inline piggyback, increasing ACK-latency upper bound by one RPC RTT (~1 ms in-DC). **Mitigation**: ACK coalescing on the dedicated `streaming-shuffle-ack-dispatch` scheduler (**AAP §0.7.4**) bounds ACKs to <10 per second per shuffle, making RTT amplification negligible compared to block-transmission time. |
| **D5. Per-`shuffleId` fallback delegation** evaluated at `registerShuffle` time; `StreamingShuffleManager` holds a `SortShuffleManager` delegate and routes specific shuffles to it when `StreamingShuffleFallbackPolicy` triggers. Fallback is **sticky per `shuffleId`** for that shuffle's lifetime. | (a) **Binary manager-level toggle**: once any fallback condition fires, all subsequent shuffles in the `SparkEnv` lifetime route to sort path. (b) **Global rollback**: re-initialize `SparkEnv.shuffleManager` mid-lifetime (violates `SparkEnv` single-initialization invariant). (c) **Non-sticky re-evaluation**: re-evaluate fallback on every `getWriter` / `getReader` call. | Per-shuffle granularity lets the feature recover once a triggering condition clears (e.g., a transient memory spike during one stage). **SC-3** (zero regression for memory-bound) requires fine-grained fallback without penalizing subsequent shuffles. A `StreamingShuffleHandle` vs. `BaseShuffleHandle` type-match at `getWriter` / `getReader` cleanly distinguishes active-streaming from delegated paths without mutating global state, preserving the single-init invariant (**AAP §0.4.1.4**). Stickiness prevents mid-shuffle routing flips that would corrupt in-flight byte pipelines. | Complexity in `registerShuffle`: multiple handle types require disciplined type-matching in `getWriter` / `getReader`; a missed match would route data through the wrong writer. **Mitigation**: exhaustive test coverage via `StreamingShuffleFallbackPolicySuite` (four conditions × producer/consumer side) and `StreamingShuffleManagerSuite` (all dispatch branches). Scala's `match` exhaustiveness warnings catch missing handle types at compile time. |
| **D6. Reuse the executor's already-constructed `TransportContext` from `SparkEnv`** for streaming transport. `StreamingShuffleTransport.scala` obtains the client factory and server via `SparkEnv.get.blockManager.blockTransferService` or a dedicated accessor without instantiating a new `TransportContext`. | (a) **Dedicated `TransportContext` instance** on a separate port (requires new port allocation, security configuration, firewall rules). (b) **Custom `ChannelPipeline`** built from bare Netty `NioEventLoopGroup` (bypasses all Spark transport conventions). (c) **HTTP/2 or gRPC transport** layered on top of Netty. | **ID-3** directive — "least modification to network transport layer". **IC-4** explicitly states "Leverage existing `org.apache.spark.network.TransportContext`". `TransportContext` already provides authenticated (SASL/SSL), configured, OOM-aware (**ADR-004**) client/server factory. No new port allocation, no new security configuration, and streaming traffic inherits `spark.authenticate` and `spark.network.crypto.enabled` automatically (**AAP §0.7.5**). A new context would double event-loop threads on each executor. | Streaming traffic shares bandwidth with other transport clients (block fetcher, RPC, push-based shuffle). **Mitigation**: QoS prioritization (**IC-5**: shuffle traffic priority over speculative tasks) and token-bucket rate limiting (**CR-B-2**) ensure streaming does not starve other clients. `NettyUtils.freeDirectMemory()` is consulted before envelope `ByteBuf` allocation to honor **ADR-004** global OOM backoff. |
| **D7. 100 ms scheduled polling of `MemoryManager`** via a single-thread `ScheduledExecutorService` named `"streaming-shuffle-memory-poll"`; combined with event-driven fallback on `acquireExecutionMemory` returning less than requested. | (a) **Pure event-driven**: hook into `MemoryManager.acquireExecutionMemory` to detect pressure inline (requires modifying `MemoryManager`, violating **AP** of executor memory model neutrality). (b) **10 ms high-frequency polling** for lower latency response. (c) **1 s low-frequency polling** to minimize overhead. | **CR-S-1** explicitly specifies "100ms polling of memory manager". **SC-5** requires "<100ms response time" — 100 ms polling plus the downstream `MemorySpillManager.trigger` dispatch yields worst-case detection-to-reclamation latency ≤ 200 ms, acceptable per SC-5's framing (polling is detection; reclamation is response). Event-driven would require editing `MemoryManager`, violating **ID-3** ("least modification to executor memory model"). 10 ms polling would double CPU overhead, risking **IC-14** (<1% CPU). 1 s polling is too coarse for SC-5's <100 ms bound. | 100 ms polling has up to 100 ms detection latency — at the edge of **SC-5**. **Mitigation**: combined with an event-driven fallback path — when `acquireExecutionMemory(n)` returns less than `n`, the writer immediately signals `MemorySpillManager.trigger()` without waiting for the next poll tick. This hybrid strategy achieves both low steady-state overhead and bounded worst-case response. |
| **D8. LRU eviction with largest-partition tie-breaking** implemented via `java.util.LinkedHashMap` with `accessOrder=true` plus an external size map. When utilization ≥ `spillThreshold`, evict the LRU partition; break ties by buffered-size descending. | (a) **Pure FIFO eviction** — oldest partition first regardless of access pattern. (b) **Size-weighted round-robin** — spill proportional fraction from every partition. (c) **Random eviction** — pick any partition uniformly. (d) **Manual priority queue** — heap keyed on `(lastAccessNanos, bufferedBytes)`. | **CR-S-2** specifies "LRU-based eviction of largest buffered partitions at 80% threshold". LRU ensures hot partitions remain in memory, aligning with access-locality observed in groupBy / join workloads. Largest-first tie-breaking maximizes memory reclaimed per spill operation, reducing spill frequency and satisfying **IC-14** (<1% CPU). `LinkedHashMap(accessOrder=true)` provides O(1) LRU maintenance for free; only the size-tie-break scan runs at the 100 ms poll boundary, not per-write. | LRU metadata maintenance is O(1) per access but the size map requires synchronized updates on every write. **Mitigation**: size map uses `ConcurrentHashMap<Integer, AtomicLong>` so updates are lock-free. Largest-first scan runs on the poll thread, never on the hot write path. |
| **D9. Fixed 2 MB maximum envelope payload size**. `StreamingShuffleWriter` fragments records exceeding 2 MB across multiple envelopes; `StreamingShuffleReader` reassembles by `(shuffleId, mapId, reduceId, sequenceNumber)` tuple. | (a) **Adaptive block sizing** based on measured network RTT and consumer consumption rate. (b) **Smaller 512 KB cap** for lower first-byte latency. (c) **Larger 8 MB cap** matching the default `spark.shuffle.file.buffer` size. (d) **Unbounded envelopes** sized to whole records. | **IC-7** explicitly states "Block size limited to 2MB for pipelining efficiency". 2 MB balances (i) Netty `ByteBuf` allocation amortization (pooled allocator prefers ≥1 MB chunks), (ii) TCP window sizing (default initial window is 1 MB; two envelopes fit one RTT), (iii) memory granularity relative to the 20% per-partition buffer cap (**IC-1**), and (iv) checksum CPU cost (one CRC32C pass covers ≤2 MB in <2 ms on modern x86). User fixed the bound; adaptive sizing adds substantial complexity without a measured benefit. | Workloads with single records > 2 MB require record splitting. **Mitigation**: `StreamingShuffleWriter` fragments records across envelope boundaries carrying a `sequenceNumber`; **CR-R-1** reader reconstructs in order, buffering fragments per `(shuffleId, mapId, reduceId)` until a complete record arrives. Record splitting is transparent to application code. |
| **D10. `BackpressureRpcEndpoint` registered only on executors**; driver-side registration is explicitly guarded by a check on `SparkEnv.get.executorId == SparkContext.DRIVER_IDENTIFIER` at endpoint-setup time. | (a) **Register on both driver and executor** unconditionally. (b) **Require driver-side centralized coordination** for cross-executor backpressure. (c) **Register on driver only** and proxy executor requests through it. | **AAP §0.7.5** security requirement: "The `BackpressureRpcEndpoint` MUST be registered only on executors, never on the driver; driver-side construction is defended by a check on `SparkEnv.get.executorId == SparkContext.DRIVER_IDENTIFIER` at endpoint-setup time." The driver performs no shuffle writes/reads; endpoint presence there would be (i) a dead RPC surface that could be enumerated, (ii) an attack vector for forged backpressure messages, and (iii) a violation of the least-privilege principle. Decentralized per-executor backpressure scales horizontally with cluster size (**CR-B-4**). | Loss of centralized view of global network saturation (driver cannot see per-executor rates). **Mitigation**: each executor monitors its own capacity; **FB-3** (90% network saturation) is evaluated locally per-executor. Cluster-wide aggregation is available through the existing Dropwizard metrics sinks (JMX, Prometheus) reading `shuffle.streaming.backpressureEvents` counters at a central scraper. |

Zero new entries to `project/MimaExcludes.scala`**; all streaming classes are either `private[spark]` or reside in the new `org.apache.spark.shuffle.streaming.*` sub-package. | (a) **Expose `@DeveloperApi` streaming classes** for third-party extensibility and add targeted MiMa exclusions for future signature changes. (b) **Extend `MimaExcludes.scala`** with broad sub-package ignores. (c) **Mark classes `@Unstable`** (no MiMa impact in Scala 2.13 but signals instability). | **AAP §0.7.8 invariant** — "Zero entries added to `project/MimaExcludes.scala`." **F-017** mandates a clean MiMa gate at `build/sbt -mem 5632 mimaReportBinaryIssues`. `private[spark]` visibility plus a new sub-package means MiMa tracks no new public surface, so the gate passes unchanged. V1 does not require third-party extensibility; promotion to `@DeveloperApi` is deferrable to a future version with proper MiMa hygiene at that time. | Third-party extension of streaming shuffle is not possible in v1 — downstream projects cannot subclass `StreamingShuffleManager` or `StreamingShuffleWriter`. **Mitigation**: documented as intentional future work in this log; the `spark.shuffle.manager` property still accepts an FQCN for teams needing entirely custom managers, and v1 streaming classes can be promoted to `@DeveloperApi` in v2 without breaking existing internal callers. |
| **D12. Opt-in activation via `spark.shuffle.manager=streaming`; configuration changes require executor restart**. No dynamic reconfiguration in v1. | (a) **Hot-reload the `ShuffleManager`** at runtime via RPC signal. (b) **Dual-manager mode** where both sort and streaming are initialized and a per-shuffle `spark.shuffle.preferStreaming` flag selects at `registerShuffle` time. (c) **Auto-detect workload** heuristics selecting streaming based on observed partition count and data volume. | **IC-13** explicitly states "Configuration changes require executor restart (no dynamic reconfiguration in v1)". `SparkEnv.initializeShuffleManager()` enforces single-bind via `Preconditions.checkState(null == _shuffleManager)` (**AAP §0.4.1.4**) — hot-reload would violate this invariant and require executor lifecycle changes (**AP-3** violation). Dual-manager mode doubles the memory footprint of the shuffle subsystem (two managers, two RPC endpoints, two metric sources). Auto-detection adds a decision surface requiring its own validation and would delay cluster-wide adoption. | Operators enabling streaming shuffle must coordinate an executor restart, interrupting running applications. **Mitigation**: `spark.dynamicAllocation.enabled=true` combined with `spark.decommission.enabled=true` and `spark.storage.decommission.shuffleBlocks.enabled=true` enables rolling restarts without cluster-wide downtime. The restart requirement is clearly documented in `docs/configuration.md` and `docs/core-migration-guide.md`. |
| **D13. Reuse `ShuffleBlockId(shuffleId, mapId, reduceId)` naming for spilled streaming blocks**. `MemorySpillManager` persists via `BlockManager.putBytes(ShuffleBlockId(...), bytes, StorageLevel.DISK_ONLY)` under the existing block-id convention. | (a) **Introduce `StreamingShuffleBlockId`** as a new `BlockId` subtype encoding streaming-specific producer state. (b) **Use `RDDBlockId`** to sidestep shuffle-id semantics. (c) **Generate synthetic UUID-keyed blocks** and track mapping in a streaming-specific index. | Consistency with `BlockManager` conventions preserves the zero-touch contract on block-manager storage interfaces (**AAP §0.6.2**, explicit scope exclusion: "Block-manager storage interface contracts"). Using the existing `ShuffleBlockId` hierarchy means spilled streaming blocks are transparently discoverable by `BlockManagerDecommissioner`, `FallbackStorage`, and `MigratableResolver` without any streaming-specific integration. A new subtype would require updating serializers, resolvers, and decommission logic — violating **ID-1** ("Make only changes necessary"). | Risk of collision between sort-path `ShuffleBlockId(s, m, r)` and streaming-path `ShuffleBlockId(s, m, r)` if a shuffle transitions mid-lifetime. **Mitigation**: the fallback policy (D5) is sticky per `shuffleId`, so a given `shuffleId` is either sort-path or streaming-path for its whole lifetime — never both. Thus no two writers ever produce the same `ShuffleBlockId` tuple for the same shuffle. |
| **D14. Explicit partition-count upper bound of `Int.MaxValue / 2`** enforced at `StreamingShuffleManager.registerShuffle`; abort with a clear error message on overflow. | (a) **Match sort path's 16,777,216 cap** (`PackedRecordPointer.MAXIMUM_PARTITION_ID + 1`). (b) **No explicit cap** (inherit whatever limit the data structures impose implicitly). (c) **Configurable cap** via `spark.shuffle.streaming.maxPartitions`. | **AAP §0.7.4** directive: "Partition count upper bound MUST be explicitly validated at `registerShuffle`; the user's specification does not mention a hard cap, so the feature MUST validate `numPartitions ≤ Int.MaxValue / 2` and abort with a clear error message otherwise." The sort path's 16,777,216 cap is a consequence of `PackedRecordPointer`'s 24-bit field — streaming does not use `PackedRecordPointer`, so that mechanical cap does not apply. However a sane bound is still required because per-partition buffer maps, ACK tables, and rate-limiter state all consume O(numPartitions) memory. `Int.MaxValue / 2` leaves headroom for internal array-size growth (doubling heuristics) without overflow. | A theoretical workload needing >1 billion partitions would be rejected. **Mitigation**: such a workload is astronomically unlikely in practice (the largest reported Spark shuffles use low-single-digit-million partition counts), and the rejection error message directs users to either increase executor count (reducing partitions per executor) or fall back to sort path. |
| **D15. Default log level `INFO` for `org.apache.spark.shuffle.streaming` package**; per-shuffle lifecycle events at `TRACE`; `DEBUG` enabled via `spark.shuffle.streaming.debug=true`. | (a) **`DEBUG` by default** for richer troubleshooting but higher log volume. (b) **`WARN` by default** to minimize noise. (c) **Always `TRACE` but buffered in a ring and flushed only on errors**. | **IC-15** bounds log volume at <10 MB/hour per executor for streaming events; `INFO` default with `TRACE` per-shuffle keeps steady-state volume well below that ceiling (empirically ~2 MB/hour per executor at typical workloads). **IC-17** specifies "Debug logging disabled by default (enable via `spark.shuffle.streaming.debug=true`)" — the debug flag temporarily elevates the package logger to `DEBUG` without editing Log4j2 configuration files, matching the operational ergonomics of existing Spark debug flags. | Operators troubleshooting performance issues may miss per-shuffle details at `INFO`. **Mitigation**: structured `LogKey` entries (`BUFFER_UTILIZATION_PERCENT`, `SPILL_COUNT`, `BACKPRESSURE_EVENTS`, `PARTIAL_READ_INVALIDATIONS`) embed diagnostic context in every `INFO`-level log line via MDC, and the four Dropwizard counters expose the same signals for real-time dashboards without log-parsing. |
| **D16. Consult `NettyUtils.freeDirectMemory()` before every envelope `ByteBuf` allocation**; respect the global `TransportContext.isNettyOOMOnShuffle` `AtomicBoolean` backoff flag. | (a) **Best-effort allocate-and-recover** — attempt allocation, catch `OutOfDirectMemoryError`, degrade gracefully. (b) **Fixed pre-allocated pool** of envelope buffers sized at executor start. (c) **Ignore direct memory** and rely on heap `ByteBuf` only. | **ADR-004** compliance — "bounded concurrent fetch with Netty OOM global backoff" (**AAP §0.7.2**). When `isNettyOOMOnShuffle` is set by any transport component that observed a direct-memory OOM, all streaming writers must stop allocating new `ByteBuf` instances until the flag clears; this prevents cascading OOM across concurrent shuffles. Pre-emptive `freeDirectMemory()` check plus flag consultation is substantially cheaper than catching `OutOfDirectMemoryError` (which requires stack unwinding and per-allocation try/catch overhead). Heap-only `ByteBuf` would force a copy at the Netty layer, doubling allocation cost. | `freeDirectMemory()` returns a snapshot; by the time allocation proceeds, another thread may have consumed the remaining budget. **Mitigation**: after the snapshot check, allocation still uses Netty's pooled allocator which maintains its own per-thread-pool accounting; on allocation failure, the writer falls back to spill and the `isNettyOOMOnShuffle` flag is set, stopping the cascade at the first failure rather than amplifying it. |
| **D17. v1 stubs for transport and reader — foundational types land in CP1; full `StreamingShuffleTransport` and `StreamingShuffleReader` behavior lands in later checkpoints.** CP1 ships `StreamingBlockEnvelope` (the wire frame), `StreamingShuffleHandle` (the dispatch marker), and `StreamingShuffleMetrics` (the observability source); the transport glue and reader iterator are scheduled for subsequent checkpoints once the manager and writer are in place. | (a) **Land the complete streaming shuffle stack in a single commit** — transport, reader, writer, backpressure, spill manager, and fallback policy together. (b) **Land the transport and reader as empty-method stubs in CP1** so the package compiles end-to-end from day one. (c) **Inline the transport and reader as private helpers** on `StreamingShuffleWriter` and merge them into its file. | **ID-1** directive — "Make only changes necessary to implement streaming shuffle capability within `ShuffleManager` abstraction boundary." A single-commit stack would concentrate risk, inflate review surface, and violate the Segmented PR Review rule (**AAP §0.7.7**) which mandates incremental, reviewable checkpoints. Empty-method stubs (option b) would introduce dead code and violate the **Zero Placeholder Policy** (**AAP §0.5 CQ**, "NO placeholder implementations or stub methods"). Phased delivery lets each checkpoint be independently reviewed, compiled, MiMa-gated, and tested. The foundational types (envelope, handle, metrics source) are self-contained and exercise no caller dependencies, so they compile cleanly on their own — which is exactly why CP1 is bounded to them. | Readers of the sub-package at CP1 may be confused by the absence of a working manager/writer/reader. **Mitigation**: this decision-log row, `streaming-shuffle-traceability.md` coverage tables, and the `CODE_REVIEW.md` checkpoint ledger explicitly document the phased delivery plan, and `ShuffleManager.scala` deliberately omits the `"streaming"` short-name entry until the manager class itself lands in a later checkpoint (preserving compile correctness at every intermediate state). |
| **D18. `MemorySpillManager` self-tracking of per-partition buffered sizes via `ConcurrentHashMap[Int, AtomicLong]`**, in addition to delegating actual memory reservation to `MemoryManager.acquireExecutionMemory` / `releaseExecutionMemory`. The two accounting layers operate in tandem — `MemoryManager` owns the cluster-wide execution-memory budget; `MemorySpillManager` owns the streaming-shuffle-internal per-partition view needed for LRU eviction and largest-first tie-breaking. | (a) **Pure delegation** to `MemoryManager` with no internal state — query `MemoryManager` for per-partition sizes on every poll. (b) **Pure self-tracking** — `MemorySpillManager` owns its own slab of memory and never calls `MemoryManager`, operating as a peer allocator. (c) **Extend `MemoryManager` / `TaskMemoryManager`** to expose per-partition queries (requires modifying executor memory model). | **ID-3** directive — "least modification to executor memory model and network transport layer." `MemoryManager` is a cluster-wide accountant with no concept of shuffle-partition identity — it deliberately exposes only aggregate acquire/release semantics so consumers (sort spiller, aggregation spiller, Tungsten allocator) cannot bypass its budget enforcement. Per-shuffle partition granularity is a streaming-shuffle-internal concern (LRU / largest-first eviction per **CR-S-2** / **D8**), and pushing it into `MemoryManager` would bloat the executor memory model with consumer-specific metadata (**AP-4** violation). Pure delegation (option a) would require scanning all `MemoryManager` consumers on every 100 ms poll — O(numConsumers × numPartitions) work per tick. Pure self-tracking (option b) would bypass the cluster-wide execution-memory budget, creating a blind spot where streaming shuffle could starve other memory consumers (aggregation, broadcast, cache) during peak load. | Two-layer accounting introduces synchronization risk — the internal `AtomicLong` per-partition counter and the `MemoryManager`-reserved byte count can drift under concurrent update/release races. **Mitigation**: the per-partition map uses `ConcurrentHashMap[Int, AtomicLong]` for lock-free updates, and every `releaseExecutionMemory(n)` is paired with an `AtomicLong.addAndGet(-n)` on the same code path; reconciliation checks run at the 100 ms poll boundary, logging a warning (with `BUFFER_UTILIZATION_PERCENT` `LogKey` context) if drift exceeds 1% of the reserved total so operators can detect regressions without production fallout. |
| **D19. CP3 Manager decides the canonical path between two options: **Option 1** — Writer continues inline `putBytes` on buffer overflow, coordinator monitors but never dispatches; pros: hot-path latency is minimized (no cross-thread spill dispatch) and disk I/O stays on the writing thread which already owns the `ByteBuf`. **Option 2** — Writer reports utilization to coordinator, coordinator dispatches spill via callback to Writer, Writer performs `putBytes`; pros: centralized LRU/largest-first eviction decision and better priority arbitration across shuffles. D26 does not pre-commit — CP3 Manager chooses based on measured latency profile via `StreamingShufflePerformanceBenchmark` (T10). Writer's inline spill path (alt b) would satisfy **CR-S-2** only if the Writer maintained per-partition LRU state, duplicating work the coordinator already does; **D8** established that LRU lives in the coordinator, so keeping both paths in CP2 preserves optionality for CP3's canonical-path decision. Coordinator-only (alt c) would violate **D21** (coordinator is coordinator-only in v1 and does not hold `BlockManager` references). Symmetric constructors (alt d) would require dummy parameters that have no semantic meaning, violating **ID-1**; the natural parameter-ordering rule ("inherited parameters first, then streaming-specific parameters in consistent order") is strictly satisfied by the current asymmetric positions. | CP3 Manager integrators may be confused by the cross-file asymmetries. **Mitigation**: this decision-log entry and the `CODE_REVIEW.md` Phase 3 Backend Architecture audit explicitly call out each asymmetry and its resolution path. A performance regression could manifest if the canonical-path decision (Writer inline vs. callback) is wrong. **Mitigation**: `StreamingShufflePerformanceBenchmark` (T10) exists specifically to measure this trade-off at CP3; the canonical-path choice will be justified by benchmark data, not by guesswork. Rate-limiter dual-instance is safe at CP2 but MUST be resolved in CP3. **Mitigation**: CP3 Manager tests assert that `getRateLimiter()` on the Transport and the internal limiter on the Protocol are reference-equal (`eq`), failing fast if unification regresses. |
| **D27. `BackpressureRpcEndpoint` and `BackpressureProtocol` have independent lifecycles — endpoint `onStop()` does not cascade to `protocol.stop()`.** `BackpressureRpcEndpoint.onStop()` logs the endpoint teardown with `LogKeys.ENDPOINT_NAME` MDC but does NOT invoke `protocol.stop()` on the held `BackpressureProtocol` reference. The two components have independent lifecycles: the RPC endpoint is bound to the executor's `NettyRpcEnv` lifecycle (start on executor init, stop on executor shutdown); the protocol is bound to the `StreamingShuffleManager` lifecycle (start when Manager instantiates, stop when Manager stops). `StreamingShuffleManager.stop()` is the **sole** owner of `protocol.stop()` invocation. | (a) **Cascade stop** — `BackpressureRpcEndpoint.onStop()` calls `protocol.stop()` to guarantee coordinated teardown. (b) **Cascade start, not stop** — endpoint `onStart()` calls `protocol.start()` but `onStop()` leaves the protocol running. (c) **Shared lifecycle** — merge endpoint and protocol into a single class so lifecycle is mechanically coupled. | A `BackpressureProtocol` instance can outlive a given `BackpressureRpcEndpoint` registration. If the RPC environment is recycled (e.g., a driver reconnect that rebinds executor endpoints), the protocol — which tracks per-producer heartbeats, per-block ACKs, per-shuffle priorities — must retain its state so in-flight shuffles continue to receive acknowledgment processing. Cascade stop (alt a) would wipe state on a transient RPC reconnect, causing spurious spills and retransmissions. The protocol is designed to be shared across multiple RPC endpoints in multi-shuffle executors (though v1 has only one endpoint, the design preserves this flexibility for future multi-executor pooling). Tying lifecycle to one endpoint would prevent the protocol from surviving endpoint restarts. **ID-4** ("Isolate streaming logic in dedicated classes") favors explicit lifecycle ownership — `StreamingShuffleManager.stop()` calls `protocol.stop()` directly and also tears down the endpoint via `rpcEnv.stop(endpointRef)`, making the teardown order explicit and auditable; a cascade would hide the order and complicate reasoning. Merged class (alt c) would violate single-responsibility — the endpoint implements `ThreadSafeRpcEndpoint` with message-routing semantics; the protocol implements backpressure state with ACK-table semantics; these are independently testable concerns. **SC-4** ("Zero data loss under all failure scenarios") is better served by a protocol that survives RPC-layer transient failures — a cascade-stop design would convert a transient RPC failure into a data-loss event (in-flight blocks lose their ACK tracking and may be retransmitted or discarded). | If CP3 Manager forgets to call `protocol.stop()` in `StreamingShuffleManager.stop()`, the `streaming-shuffle-heartbeat` scheduler and any retained state will persist until JVM shutdown (daemon threads prevent process hang, but state leaks across `SparkEnv.stop()`). **Mitigation**: `StreamingShuffleManagerSuite` (T1) includes a `stop()`-idempotency test that asserts `protocol.stop()` is invoked exactly once on Manager stop; the test catches a missing stop call. Reviewers may expect a cascade based on RAII intuition. **Mitigation**: this decision-log entry documents the rationale explicitly; `BackpressureRpcEndpoint.onStop()` Scaladoc references D27 and describes the non-cascade semantics; `StreamingShuffleManager.stop()` Scaladoc enumerates the specific components it tears down. |

  the Explainability Rule (AAP §0.7.7).

### When to Add a New Decision

Add a new row to the table above when any of the following occurs:

1. A new non-obvious choice arises during implementation (e.g., choosing a
   specific `ExecutorService` shutdown strategy, selecting a concurrent data
   structure, resolving a deadlock avoidance pattern).
2. A previous decision is superseded — add a new row; do **not** edit the
   old row in place. Cite the superseded decision's ID in the new Rationale
   cell (e.g., "Supersedes D7 due to …").
3. A risk identified in an existing row materializes — add a new row
   documenting the remediation decision.

### Audit Trail Convention

Every decision row is immutable once merged. Corrections to typos, grammar,
or formatting are permitted; changes to Decision, Alternatives Considered,
Rationale, or Risks content require a superseding row as described above.
This preserves a complete historical record of the feature's design
reasoning, satisfying the Explainability Rule's "single source of truth"
requirement (AAP §0.7.7).

### Decision ID Convention

Each decision in the table is labeled `Dn.` in the Decision cell (e.g.,
`D1.`, `D7.`, `D16.`) so it can be referenced unambiguously from source
comments, commit messages, review conversations, and follow-up decision
entries. IDs are monotonically increasing and never reused; a superseding
decision receives the next unused ID rather than reusing the old one.
