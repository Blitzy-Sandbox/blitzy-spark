====================================================================================================
WHAT THIS FILE ESTABLISHES
====================================================================================================

  That QA finding F3 — "Pinned jimple2cpg cannot persist the required complete all-JAR graph" —
  still stands, that its cause is a fixed JVM array-length bound rather than a heap shortage, and
  that no action available to an executing agent under this plan can move it. Three things are
  established by measurement rather than by argument:

    1. The bound does not move with the heap. The probe that drives java.io.ByteArrayOutputStream's
       own growth path to the soft maximum array length was compiled and run in this clone at
       -Xmx8g, -Xmx64g and -Xmx128g. All three arms fail at the same byte, with the JVM's reported
       maxMemory spanning a factor of sixteen between the smallest and the largest arm.

    2. The frontend has no option that would help. Its complete option surface was enumerated
       first-hand — 12 named options and one positional argument — and is stated option by option
       below. None chunks or streams the writer, none selects an alternative output format, and the
       two options that change what the writer must represent (--full-resolver, --enable-file-content)
       both ENLARGE it.

    3. The only remedies that would work are the ones this plan prohibits. The permitted-action
       matrix below states, for each conceivable remedy, the outcome and the AAP section that
       permits or forbids it, and names the single decision a human must take.

  What this file does NOT do: it does not rebuild the graph. No jimple2cpg invocation over any real
  input set was made by this pass, no code-property graph was loaded, and no 64 GiB Joern JVM was
  started. F3 is a halt-and-report condition, and this file is the report's evidence, not an attempt
  at a workaround.

====================================================================================================
WHY IT MATTERS HERE
====================================================================================================

  AAP 0.1.1 requires the graph to be created by this run over every JAR the build produced, and
  persisted. AAP 0.3.2 forbids trimming that input set — "No trimming of the graph input set, and no
  exclusion of any JAR the build produced" — and AAP 0.4.3 forbids installing, upgrading or
  substituting any tool. flatgraph 0.1.32, the writer the pinned Joern 4.0.607 ships, serialises the
  graph's ENTIRE deduplicated string pool by UTF-8 encoding each string and appending it to ONE
  java.io.ByteArrayOutputStream (flatgraph.storage.WriterContext.finish, Serialization.scala:174-176).
  A ByteArrayOutputStream is backed by a single contiguous byte[], and the JVM caps an array at
  Integer.MAX_VALUE - 8 = 2,147,483,639 elements.

  Over the complete input set the full reactor produces, that pool exceeds the cap, so the frontend
  throws AFTER the graph is already built in memory and writes no usable graph. Two independent
  invocations have hit it: the lane recorded in harness/artifacts/logs/cpg-frontend.log, and QA's own
  attempt reported as F3. Raising the heap cannot move a bound on one array's length. The three arms
  below are the measurement that says so, taken in this clone rather than cited from either lane.

  The JVM's reported maxMemory spans a factor of sixteen across the three arms, and the failure point
  does not move by one byte: the same 2,147,483,639 bytes are already buffered in every arm, and the
  same next write is refused. The bound is therefore on the length of ONE array — Integer.MAX_VALUE - 8
  — and not on the heap. The 8 GiB arm is the strongest single line of this table: a heap eight times
  SMALLER than the plan's minimum still reaches the ceiling, so nothing between 8 GiB and 128 GiB is
  the constraint.

  What the bound scales with follows from what the writer does: the total UTF-8 size of the graph's
  distinct strings — method full names, type full names, file names, literals — that is, the BREADTH
  of the input set. It does not scale with the memory or the time spent building the graph, which is
  why the recorded lane failed with 113.3 GiB resident inside a 128 GiB heap after eight hours of
  successful work.

  Note on the addend: the "+ 77" here is the length the retained probe source fixes. The frontend's
  own runs reported "+ 72" (the lane in cpg-frontend.log) and "+ 76" (QA's lane in F3). The addend is
  simply the next string's UTF-8 length; the bound, 2,147,483,639, is identical in all cases, and it
  is the bound that decides the outcome.

THE PERMITTED-ACTION MATRIX
====================================================================================================

  Each row states the remedy, what it would actually do to the bound, and the AAP section that
  permits or forbids it. "Would work" and "is permitted" are different columns on purpose: the two
  remedies that would work are the two the plan forbids, which is exactly why F3 is a human decision.

  1. RAISE THE HEAP further (256 GiB, 512 GiB, any value)
     Outcome            Does not move the bound. Measured: arms A, B and C fail at the same byte
                        across a sixteen-fold heap range. The recorded lane was already resident at
                        113.3 GiB inside a 128 GiB heap when it failed.
     Plan               PERMITTED but useless. AAP 0.5.4 / 0.8.2: "raising a heap is permitted and
                        reported, lowering one produces a truncated graph whose silence cannot be
                        distinguished from a clean result." Raising is therefore allowed and has
                        already been done (64 GiB minimum -> 128 GiB); it changes nothing here.
     Verdict            AVAILABLE, INEFFECTIVE.

  2. TRIM THE INPUT SET — --exclude, --exclude-regex, --depth, or dropping pre-shade, -tests or
     shims archives
     Outcome            WOULD WORK. The bound scales with the total UTF-8 size of the graph's
                        distinct strings, so a narrower input set serialises. The narrower witness
                        graph recorded in cpg-frontend.log PART 2 is the corroboration: 38 primary
                        artifacts, 52,584 class entries, written successfully at 418,777,229 bytes.
     Plan               FORBIDDEN. AAP 0.3.2: "No trimming of the graph input set, and no exclusion

                        nothing" — "not the connect-shims artifact, not a -tests artifact, not a
                        pre-shade sibling." AAP 0.2.1: "The input set is never trimmed in either
                        direction to make a number fit." AAP 0.8.2 repeats it as a process
                        constraint, and AAP 0.9.2's own preamble makes the disposition explicit:
                        "These are reported, not repaired."
     Verdict            EFFECTIVE, PROHIBITED. Not taken.

  3. UPGRADE OR SUBSTITUTE JOERN / FLATGRAPH for a version whose writer chunks or streams the pool
     Outcome            WOULD WORK, and is the only remedy that both fixes the root cause and keeps
                        the mandated input set intact.
     Plan               FORBIDDEN to this run. AAP 0.4.3: "None, in any direction. No dependency is

                        substituting any tool are prohibited. AAP 0.8.1: "Nothing is installed,
                        upgraded, substituted or provisioned." A missing or inadequate tool is a
                        halt-and-report, never a repair task.
     Verdict            EFFECTIVE, PROHIBITED to an executing agent. This is one of the two forms
                        the human decision can take.

  4. USE A FRONTEND OPTION that chunks, streams, or changes the output format
     Outcome            NO SUCH OPTION EXISTS. Measured first-hand above: 12 named options and one
                        positional argument, none of which touches the writer's buffering, and two
                        of which (--full-resolver, --enable-file-content) enlarge the pool.
     Plan               Moot — there is nothing to permit or forbid.
     Verdict            UNAVAILABLE.

  5. WRITE THE GRAPH IN PARTS — split the input, persist per part, merge; or build in memory and
     query in-process without persisting
     Outcome            No merge exists in the pinned distribution, and a merged graph would carry
                        the same deduplicated string pool and hit the same bound at write time. An
                        in-process graph is never persisted, so it has no identity to record.
     Plan               NOT COMPLIANT. AAP 0.1.1 requires the graph persisted; AAP 0.5.1 and 0.6.4
                        require ONE graph whose byte size and sha256 are recorded at write time and
                        "recomputed and compared immediately before every one of those loads", and
                        the runners read it from disk by path. Splitting the input is also row 2 by
                        another name.
     Verdict            UNAVAILABLE and NON-COMPLIANT.

  6. ACCEPT THE PARTIAL FILE — link it at the sanctioned path, or import it
     Outcome            It is a truncated write from a terminated serialization, not a graph. Every
                        count taken from it would be a finding about a broken write wearing the
                        shape of a finding about Spark.
     Plan               FORBIDDEN. AAP 0.2.1 and 0.9.2: a truncated graph's silence is
                        indistinguishable from a clean result, which is why a graph whose size or
                        digest differs from the value recorded at write time halts the run at any
                        later load. Both lanes handled this correctly and neither loaded its partial:
                        QA's 695,829,405-byte file was marked DO-NOT-IMPORT and never loaded, and the
                        recorded lane's 691,541,019-byte file was renamed
                        spark.cpg.PARTIAL-TRUNCATED-DO-NOT-LOAD, never linked at harness/cpg/spark.cpg
                        and loaded by no stage. Importing a partial graph is not an option, and
                        nothing in this pass loaded either file.
     Verdict            PROHIBITED and UNSAFE. Not taken.

  7. PRESENT THE INHERITED, PROVISIONED GRAPH AS THIS RUN'S GRAPH
     Outcome            It is a real, loadable graph, but it was written by provisioning over a
                        different input set. It does not satisfy the requirement that this run create
                        the graph.
     Plan               PERMITTED ONLY AS A LABELLED DIVERGENCE, never as satisfaction. AAP 0.1.3's
                        authority rule and AAP 0.9.4: "every divergence is in the record ... each with
                        both the expected and the observed value." That is how the run already handled
                        it, and F3 stands regardless.
     Verdict            NOT SATISFACTION. Already reported as a divergence.

  THE SINGLE DECISION A HUMAN MUST TAKE
    One decision, with exactly two admissible forms, and no third:

      (a) Amend AAP 0.4.3 / 0.8.1 to authorise re-provisioning a Joern/flatgraph whose graph writer
          chunks or streams the string pool, and rebuild the graph over the unchanged complete input
          set; or
      (b) Amend AAP 0.1.1 / 0.3.2 / 0.5.1's single-complete-graph-over-every-JAR requirement — for
          example to accept a partitioned set of per-part graphs, each with its own recorded
          identity, as compliant input.

    Both are amendments to the plan's own prohibitions, so both are outside an executing agent's
    authority. Nothing an executing agent may do moves a bound on one array's length, which is why
    this is reported rather than repaired.

====================================================================================================
CONSEQUENCE, STATED PLAINLY
====================================================================================================

  F3's condition still stands, unchanged and unrepairable within this plan. A graph over every JAR the
  full reactor produced cannot be persisted by the pinned frontend at this pin, at any heap: the write
  fails inside flatgraph's string-pool writer at a fixed 2,147,483,639-byte array bound, and this pass
  measured that same bound at 8 GiB, 64 GiB and 128 GiB with the failure point not moving by one byte.
  The frontend's own 12-option surface offers no chunking, no streaming and no alternative output
  format, and the two remedies that would work — trimming the input set, or substituting the writer —
  are the two the plan forbids.

  So the disposition is halt-and-report, and this file is the report's first-hand evidence. No graph
  was rebuilt by this pass, no partial graph was imported, no input set was trimmed, no tool was
  installed, upgraded or substituted, no heap was lowered, and no pre-existing file was modified. The
  requirement stays published as an unmet divergence, the graph the Joern stages load stays named,
  digested and re-verified before every load with its provisioned provenance stated wherever it is
  cited, and no coverage conclusion is drawn from bytecode the graph does not contain.

  It waits on one human decision, in one of the two forms named above.
