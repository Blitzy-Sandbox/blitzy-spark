================================================================================
WHAT THIS FILE ESTABLISHES
================================================================================
  What the pinned Opengrep engine can and cannot be told to do about taint,
  captured from the engine itself in THIS clone rather than cited from any
  record. It exists because QA finding F5 reports the AAP-mandated taint A/B
  (AAP 0.5.1, 0.9.1) as non-discriminating on its mandated subject, and the
  first question any reader asks is whether a genuinely taint-free arm could
  have been constructed instead. This file answers that from the engine's own
  option list: it carries `opengrep --version`, the COMPLETE verbatim text of
  `opengrep scan --help`, an enumeration of every option whose name or help
  text mentions taint, dataflow, pro, interfile or optimization with a verdict
  for each, two controls that were RUN rather than read, and an explicit
  conclusion.

  Companion files, same measurement pass:
    harness/artifacts/logs/reverification-f5-taint-ab.log   (human-readable record)
    harness/artifacts/logs/reverification-f5-taint-ab.json  (machine-readable record)

================================================================================
WHY THIS FILE IS UNDER logs/ AND NEVER UNDER raw/
================================================================================
  raw/ is RUNNER-ONLY: it receives exactly one artifact per tool that writes
  one and nothing else, ever (AAP 0.5.1, 0.6.1). Opengrep appears twice in
  this run by design - once as one of the nine scanned runners, whose
  artifact is harness/artifacts/raw/opengrep.sarif, and once as the taint
  A/B subject. This capture and every SARIF of this measurement pass belong
  to the second appearance, which writes outside raw/ and contributes NO
  dataset row (AAP 0.3.2). A file of this pass landing in raw/ would
  overwrite the Stage 3 runner's artifact and the dataset would then be
  built from an option capture instead of a scan.

SECTION 4 - EVERY OPTION MENTIONING taint / dataflow / pro / interfile /
            optimization, AND WHETHER IT CAN DISABLE TAINT
================================================================================
  Selection is mechanical: an option block qualifies if its NAME or its HELP
  TEXT contains taint, dataflow, pro, interfile or optimi(zation). That
  substring test is deliberately loose - it catches 'postprocess', 'profile',
  'project' and 'provides' as well - and every such match is listed rather
  than quietly dropped, with the substring named. 21 of the 101 option blocks
  qualify.

  --taint-intrafile   (help line 445)
    matched on      : name+help: taint
    what it does    : THE SETTING THIS A/B TOGGLES. 'Enable intra-file inter-
                      procedural taint analysis. Supported languages: ...
                      Scala ... Other languages will fall back to
                      intraprocedural analysis only.'
    disables taint? : NO - it ENABLES an additional inter-procedural layer.
                      Its own help text says the fallback is 'intraprocedural
                      analysis only', i.e. taint still runs without it.

  --guarded-taint-signatures   (help line 192)
    matched on      : name+help: taint
    what it does    : 'Attach branch-condition guards to taint effects and
                      evaluate them at call sites, dropping effects whose
                      guard is false.' REQUIRES --experimental.
    disables taint? : NO - it refines which taint effects survive; it neither
                      switches the engine off nor is usable without
                      --experimental.

  --dataflow-traces   (help line 56)
    matched on      : name: dataflow
    what it does    : 'Explain how non-local values reach the location of a
                      finding (only affects text and SARIF output).'
    disables taint? : NO - presentation only, and its own help says it only
                      affects output. Dropping it would remove the codeFlow
                      from the SARIF, not the taint analysis that produced the
                      finding.

  --optimizations   (help line 343)
    matched on      : name+help: optimization
    what it does    : 'Turn on/off optimizations. Default = all. Use none to
                      turn all optimizations off.'
    disables taint? : NO - MEASURED, not assumed: with --optimizations=none
                      the pinned rule still returns 1 finding at
                      DiskStore.scala:72 carrying a codeFlow (SECTION 4,
                      control 2).

  --pro   (help line 356)
    matched on      : name+help: pro
    what it does    : 'Inter-file analysis and Pro languages ... Requires
                      Semgrep Pro Engine.'
    disables taint? : NO - and unavailable: it requires the proprietary Pro

SECTION 5 - CONCLUSION
================================================================================
  NO OPTION AT THIS PIN DISABLES THE TAINT ENGINE. Of the 101 option blocks
  `opengrep scan --help` documents at version 1.27.1, exactly two carry 'taint'
  in their name: --taint-intrafile, which ENABLES an intra-file
  inter-procedural layer on top of taint, and --guarded-taint-signatures,
  which drops guarded taint effects and is gated behind --experimental.
  --dataflow-traces changes output only, by its own words. --optimizations
  =none was RUN and still produced the taint finding. The --pro family
  requires an engine this run may not install and would add taint rather
  than remove it. None of the 12 `--no-*` options concerns taint.

  TWO CONSEQUENCES, STATED PLAINLY.

  First: 'taint off' in the AAP's mandated pair does not mean 'no taint'. It
  means INTRAPROCEDURAL TAINT - the engine's documented fallback when
  --taint-intrafile is absent. The A/B as specified therefore contrasts
  intraprocedural taint against intra-file inter-procedural taint, and on a
  subject whose source and sink share one method there is nothing for the
  second to add. That is a property of the specified pair, not a defect in
  the engine and not something a flag can repair.

  Second: a truly taint-free arm is NOT CONSTRUCTIBLE with this engine. The
  only way to obtain one is to change the RULE rather than the engine - which
  is what the source-removed control in reverification-f5-taint-ab.log does,
  by replacing the rule's pattern-sources with an unmatchable marker while
  leaving `mode: taint` and every sink intact. That control returns 0 findings
  against the real rule's 1 at line 72, so it establishes what the mandated
  pair cannot: the line-72 result is produced by source-to-sink taint
  propagation and not by a syntactic sink match. It is a control, not a
  substitute for the mandated pair, and the mandated pair's failure stands
  unrepaired (AAP 0.9.2).
