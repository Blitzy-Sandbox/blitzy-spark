## 3. Severity Rubric

> **Severity Rubric (deterministic):**
>
> - **critical** — Exploitable unauthenticated remote code execution; authentication bypass; bundled library at a known critical-CVE version with active exploit in the default code path.
> - **high** — Exploitable with simple preconditions (e.g., authenticated user, default config); cryptographic weakness exploitable in practice; broken cryptographic algorithm in a default code path; unauthenticated network listener on a default port even if mitigation guidance exists.
> - **medium** — Requires non-default configuration; weakened-but-not-broken crypto; insecure defaults that can be overridden by an operator; backwards-compatibility-only weak ciphers; transitive CVEs in dependencies whose call paths are not reached in default configurations.
> - **low** — Defense-in-depth gap; hardening miss; logging hygiene; input validation for already-authenticated identities; EOL-but-not-CVE'd dependencies; watchpoint dependencies pending future remediation.

The rubric is applied deterministically: a single observed pattern always maps to the same severity tier across the audit, and tier choice is documented for every case where the next tier up or down could be defended.

| Decision | Alternatives Considered | Chosen Option | Rationale | Risks |
|----------|-------------------------|---------------|-----------|-------|

## 7. Open Questions and Limitations

> **Open Questions:**
> - The audit did not execute Spark and therefore did not validate findings dynamically. False positives are possible where defensive controls exist outside the inspected file (e.g., a Servlet filter chain that intercepts a request before reaching a sink that *looks* unauthenticated when read in isolation).
> - The audit did not consult `cwe.mitre.org` at runtime; CWE assignments are based on the agent's training-time knowledge of the catalog. If a CWE has been deprecated or had its scope amended after the training cutoff, the assignment may need revision.
> - The five-pass pipeline does not include a dedicated supply-chain pass for GitHub Actions third-party action pinning, beyond surfacing obvious untrusted-input expansions; some workflow-level risks may be deferred to a future Config.
>
> **Limitations:**
> - Native-analysis-only Config (this run) does not produce confidence scores per finding; per-finding confidence is a downstream Config feature reserved for tool-augmented runs that emit native confidence metadata.
> - Findings against vendored third-party code (e.g., `python/pyspark/cloudpickle/`) cannot be resolved by upgrading a dependency declaration; this is a structural limitation of the bundling decision rather than the audit.
> - The audit produces zero remediation suggestions; the severity rubric and description text are the only signals communicated through the JSON file. Remediation is a downstream activity per AAP §0.3.2.
> - Line numbers point to the most actionable single line for multi-line patterns (e.g., the `Cipher.getInstance(...)` invocation, not the import or the surrounding method signature). Reviewers should expand context around each line when triaging.
> - The 200-character description cap forces concise descriptions; longer rationale lives in this decision log (this is the §2 row 3 trade-off in operation).
